# 解构 → 热度补充 → 压缩提炼：方法论（Step 3–5）

三步各有输入和产出，按顺序做。Step 3 和 Step 4 的中间产物写进 `analysis_notes.md`（可以写得粗糙、可以很长），Step 5 再从笔记里压缩成 `digest.json`。

---

## Step 3 · 解构（基于 transcript_zh.md）

### 3.1 内容框架

目标：还原访谈的**逻辑骨架**。它不一定按时间顺序，但每个节点都要落回时间轴。

1. 先看 `meta.json.chapters`（创作者章节）。有章节就以章节为初稿，没有就按话题切换点自己切。
2. 每个框架节点需要：`title`（≤ 14 字，用判断句，不要只写名词，比如写「路线图是伪计划」，不写「关于路线图」）、`start` / `end`、`summary`（1–2 句）、`points`（2–4 个带时间戳的要点）。
3. 节点数量：≤ 30 分钟 3–5 个；30–90 分钟 5–8 个；> 90 分钟 7–10 个。超出就合并相近话题。
4. 识别访谈的**叙事结构**，写在 `analysis_notes.md` 里，Step 5 的 `one_liner` 和 `value.why` 会用到。常见结构有：
   - 经历线：起点 → 转折 → 方法论 → 反思
   - 论证线：主张 → 论据 → 反驳 → 修正
   - 清单线：N 条建议 / N 个误区
   - 对谈线：主持人追问驱动，嘉宾逐层展开

5. **冷开场（cold open）**：很多播客开头 1–2 分钟是把后文精彩片段剪在一起的预告。识别方法：开头出现一连串短问短答，之后主持人才说「Today my guest is…」。框架的第一个节点可以从 00:00 开始，但**所有观点、金句、要点的时间戳都要指向正文里完整讨论的位置**，不要指向预告。render_report.py 找到同一句话出现多次时，会取离你标注最近的那一处。

### 3.2 主要观点

- **观点 = 可以被反驳的主张**。「AI 很重要」这种不算观点，「90% 的 AI 功能是找不到问题的 demo」才算。
- 每条观点记录：主张（title）、展开（detail）、论据（evidence：数据 / 案例 / 亲身经历 / 类比，注明是哪一种）、说话人、时间戳。
- 区分**嘉宾原创洞见**和**行业共识复述**。后者降权，或者直接不收。
- 数量：5–10 条，按「反常识程度 × 可操作性」排序。

### 3.3 金句

入选标准（至少满足 2 条）：
- 观点浓缩：一句话概括一个方法论
- 反常识 / 反直觉
- 有画面感或修辞：对比、比喻、排比
- 可以脱离上下文直接引用
- 评论区有人原句引用（Step 4 回填，权重最高）

硬性规则：
- `en` 字段**必须从 transcript.md 原样复制**（可以截取连续片段，不能改词）。render_report.py 会做原文比对，匹配不上就报错。
- `zh` 是润色后的译文，可以比逐句翻译更凝练，但不能改变意思。
- `why` 用一句话说明它为什么值得记。
- 数量：5–10 条。

### 3.4 观点冲突

冲突是访谈里信息密度最高的部分。按下面五类逐一排查：

| 类型 | 识别信号 | 例子 |
|---|---|---|
| 嘉宾 vs 主持人 | 主持人说 "push back / devil's advocate / but isn't…"，嘉宾回 "I disagree" | 主持人：领导层需要日期；嘉宾：他们需要的是信心 |
| 嘉宾 vs 行业共识 | "most people think… but…"、"contrarian" | DAU 是虚荣指标 |
| 嘉宾前后矛盾 | 同一话题在不同时间点的立场不一致 | 前面说 AI 是炒作，后面又说自家 AI 功能很成功 |
| 嘉宾 vs 评论区 | 高赞评论或回复明确反对（Step 4 回填） | 「DAU 对广告型产品完全适用」 |
| 嘉宾 vs 其他权威 | 嘉宾点名反驳某人或某公司的做法 | "Unlike what Spotify does…" |

每条冲突要写清双方：`a` / `b` 各自的 who、claim、t。再写 `analysis`：这个分歧的本质是什么（前提不同？适用场景不同？定义不同？），你怎么判断。**不要和稀泥**，要给出有立场的判断，比如「两者都对」之外，还要说清各自在什么条件下成立。

没有明显冲突时，至少找出 1 处「隐含张力」（嘉宾没展开、但前提值得质疑的地方），`type` 写「隐含张力」。

## Step 4 · 流量高峰 + 评论聚焦：补充内容

输入：`signals.md`（由 analyze_signals.py 生成）。

### 4.1 信号解读优先级

1. **⚡ 评论锚点和回看高峰重合**：最强信号，必须进 `hotspots`。
2. **回看高峰（P1..Pn）**：z ≥ 1.5 基本必收；z 在 1.0–1.5 之间，结合内容判断。前 3% 的开场高峰已被过滤。
3. **评论锚点**：mentions ≥ 2，或者单条评论高赞（点赞数排进前 10%）。
4. **高赞评论线程**（不带时间戳）：用来归纳 `comment_insights`，并尝试把它映射回视频时间点（例如评论说「她讲的 AI 那段」→ 在译稿里找到 AI 段落的时间戳）。

### 4.2 回看高峰的成因判断

回看不一定代表认同。每个高峰都要写 `why`，先判断属于下面哪一类（分类只用来想清楚原因，**不要把分类名当标签贴进 `why`**，要用一句话把具体原因写出来，比如「大多数人回拖是为了记书名」，不要写「资源型回看：」）：

- **干货密集**：方法论、步骤、数字，观众回看是为了记笔记
- **争议 / 反常识**：观众回看确认「他真这么说了？」
- **情绪高点**：故事、笑点、感人时刻
- **信息难懂**：语速快、术语多、口音重
- **外部原因**：画面上有图表或代码，被截图、被外部引用
- **资源型**：快问快答、书单、工具推荐，观众回拖是为了记名字。这类高峰常出现在片尾，而且往往是全片最高。遇到时在 supplement 里把清单整理出来

**冷区同样是信号**：热度值连续多个点低于均值一半的区间，说明观众在跳过，常见于广告、寒暄和泛泛而谈的段落。在 `value.why` 或 `caveats` 里点明「X–Y 分钟是冷区」，帮读者省时间。

**评论里的时间戳要分清强弱**：一条评论里列了 3 个以上时间戳，说明它是观众自制的目录，脚本会把权重平摊，并标注 `index_only`，只能当弱信号用。一条评论写的是时间范围（如「42:40 - 42:50」），只算一次。

**评论需要事实核查**：高赞评论也可能张冠李戴，比如把主持人提到的书说成嘉宾推荐。引用评论前先用译稿核对，把错误写进 supplement 或 conflicts.analysis，不要跟着传播。

### 4.3 补充（supplement）写什么

原片**没讲透**、但观众想知道的东西，写 1–3 句：
- 评论区追问但嘉宾没回答的问题：给出背景知识，或者标注「嘉宾未回应」
- 评论区的反例和反驳：回填到 `conflicts`（type = 嘉宾 vs 评论区）
- 评论区补充的数据、资源、亲身经历
- 必要的背景：人物、公司、事件。**只写确定的事实**，拿不准就标「待核实」，或者用 WebSearch 查证后再写

### 4.4 评论洞察（comment_insights）

把前 30–50 条高赞线程归为 4–8 个主题。每个主题包括：theme、stance（赞同 / 质疑 / 补充 / 求资源 / 共鸣 / 玩梗）、summary（写明大概占比和代表性观点）、likes（代表评论的点赞数）、t（能映射到视频的时间点）。玩梗类评论少量收录即可，但它能反映出圈点，不要全部丢掉。

没有评论数据时（BOT_CHECK 降级、评论被关闭），在 `value.caveats` 里注明「本报告未结合评论区数据」，`hotspots` 只基于 heatmap 或内容本身判断，`source` 写 `content`。

## Step 5 · 压缩提炼 → digest.json

### 5.1 压缩原则

- **结论先行**：`one_liner` 用一句话（≤ 40 字）说清「这期讲了什么 + 最值钱的一个判断」。
- **TL;DR**：3–6 条，每条 ≤ 50 字、带时间戳。只看这几条的读者，应该能拿走 80% 的价值。
- **去重**：同一个观点只在最合适的板块出现一次，其他地方用 `[mm:ss]` 引用，不要重复展开。
- 不同板块的职责：框架回答「怎么讲的」；观点回答「主张了什么」；金句是「原话怎么说」；冲突回答「哪里有分歧」；热点回答「观众在乎什么」。

### 5.2 访谈价值（value）

- `score`（1–5，可以有 0.5）的评分维度：信息密度、原创性、可操作性、嘉宾权威度、时效性。在 `why` 里点明加分和扣分项，别只写好话。
- `for_whom`：2–4 类具体人群（「0–1 阶段的产品负责人」，不写「对产品感兴趣的人」）。
- `takeaways`：3–5 条「看完能直接用的东西」，每条带时间戳。
- `caveats`：局限性，比如样本偏差、利益相关（嘉宾在推销自家产品）、观点过时、数据来源缺失。

### 5.3 时间戳规则（硬性要求）

- **所有总结项都要带时间戳**，指向该内容在视频中**开始被讨论**的位置（宁可早 2–3 秒，不要晚）。
- 字段格式：`"t": "12:34"` 或 `"t": 754`（秒）。
- 在任何文本字段里写 `[12:34]`，都会自动渲染成可点击的时间点，适合在一句话里引用多个位置。
- 时间戳必须来自 transcript.md / transcript_zh.md 里真实存在的段落，**禁止估算**。

### 5.4 文风

报告要读起来像一位认真看完节目的编辑写的，不像模板填出来的。

- **不用 emoji，不用感叹号。** 页面的层次靠排版表达，文字里不需要符号装饰。
- **不在文本里加粗，也不写「标签：」开头的句子。** 比如「**加分**：……**扣分**：……」「**核心观点 + 焦虑引爆点**」，改成正常的句子：「她讲了几件公司里真在做的事……不足在于……」。
- **用数字和细节代替形容词。** 不写「干货满满」「非常有价值」，写「讲了三个具体做法」「回看比第二高的片段高出七成」。数字要算对，倍数和比例写之前先核一遍。
- **避开套话和流行词**：赋能、抓手、落地、闭环、底层逻辑、本质上、干货、引爆、可抄作业、三件套、题眼、至关重要、不可谈判。能说「用」就不说「赋能」，能说「做法」就不说「抓手」。
- **少用破折号**，一句话一个意思。长句拆成两句。
- **不要为了整齐凑数。** 要点有 4 条就写 4 条，不必凑成 3 或 5；标题不用每个都写成对仗句。
- **说话人只在需要区分时写。** 所有观点都来自同一位嘉宾时，渲染器会在板块说明里写一次，不必在每条里重复。
- 判断要有立场，但语气平实。「这是整期最值得追问的地方」比「这是全片最大的亮点！」更可信。

### 5.5 自检清单（写完 digest.json 后逐项核对）

- [ ] one_liner 是判断句，不是话题描述
- [ ] 每条 tldr / point / viewpoint / quote / hotspot 都有 t
- [ ] 金句的 en 从原文复制
- [ ] conflicts ≥ 1（或者有一条「隐含张力」）
- [ ] hotspots 覆盖了 signals.md 里所有 ⚡ 项
- [ ] value.caveats 写明了数据缺失或利益相关
- [ ] 全文没有 emoji、`**`、「XX：」式标签和 5.4 里列出的套话；文中的倍数、比例和原始数据对得上
- [ ] 运行 `render_report.py --strict`，确认 errors 为空
